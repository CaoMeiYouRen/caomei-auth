## 1. 阶段目标

1. **先修事实**：让「看起来有、实际没有」的通道要么可用、要么明确不可用，杜绝「提示已发送但实际未发送」。
2. **先有可观测性**：改绑、2FA 开关、密码重置、社交 / 手机绑定留下结构化审计事件（操作人、目标、before / after、来源、结果）。
3. **给管理员一条可控的协助路径**：管理员只能**发起**改绑，用户在**新通道**确认后才生效；生效后**必须重置密码**才能登录；**不**触碰 2FA 与备份码，也不允许管理员代设密码。
4. **不制造死锁**：不做 2FA 覆盖收紧（阶段 4）、不引入恢复码与冷静期（阶段 3）、不提供管理员 2FA 重置（D4 已决策为不允许）。

## 2. 范围与非目标

### 2.1 本阶段范围

- **通道改绑基座**：待确认改绑请求的实体与仓储、一次性验证码（含确认页令牌）、过期与重放保护。
- **管理员发起**：用户详情里发起改邮箱 / 改手机，填写原因，向新通道发送验证码；移除既有的「直接编辑邮箱 / 手机」与「新密码」输入。
- **用户确认**：确认页（GET 只读、POST 消费）→ 新通道生效并置为已验证 → 撤销全部会话 → 置「必须重置密码」。
- **强制重置**：重置完成前拒绝任何登录方式；确认后自动发送重置验证码；重置成功后清标记、撤销会话、允许以新密码登录。
- **假通道修复**：短信重置通道、备份码再生成、2FA 邮件 OTP 回落与提示、改绑 / 撤销会话错误检查。
- **审计**：四条恢复路径 + 改绑发起 / 确认 / 强制重置 / 完成，全部写入结构化审计。
- **文档与文案**：`docs/standards/security.md` 补 2FA 覆盖边界与恢复等级；管理员协助恢复口径；5 语键同步。
- **UI 基线**：管理员用户详情、用户侧确认页、受影响的安全设置区块。

### 2.2 非目标

- **不做根凭据模型变更**：不引入恢复码、不改「旧邮箱确认」模型、不引入冷静期（阶段 3）。
- **不做 2FA 覆盖收紧**：邮箱 OTP / 魔法链接 / 社交 / SSO / 验证链接仍不触发 2FA（阶段 4）。
- **不提供管理员 2FA / 备份码重置**（D4，2026-11-20 决策）；用户同时丢失两者时明确告知无人工路径。
- **不提供管理员代设密码**（D8，2026-11-20 决策）；管理员上限是触发重置邮件。
- **不引入短信供应商**：短信通道按「已配置则用、未配置则明确不可用」处理。
- **不做多级审批 / 工单系统**：本阶段只要求操作原因与审计；审批留后续阶段评估。
- **不翻译用户生成内容**，不调整既有 zh-CN / en-US 语义（仅随键同步）。

## 5. 关键口径

### 5.1 审计事件

- 通道：复用 `server/utils/logger.ts` 的 audit 文件（已存在），新增结构化字段，不建审计表。
- 必填字段：`action`（channel.change.request / channel.change.confirm / channel.change.notify / twoFactor.enable / twoFactor.disable / backupCodes.regenerate / password.reset / password.reset.request / password.reset.forced / social.bind / phone.bind）、`actorId`、`targetUserId`、`before`、`after`、`result`、`reason`、`ip`、`userAgent`、`source`（web / admin）。
- 不记录密码、验证码、备份码明文；`before` / `after` 只记状态差异（脱敏后的邮箱 / 手机，如 `a***@example.com`）。

### 5.2 管理员协助恢复的不变量（D9）

1. 管理员**不能**直接修改邮箱 / 手机，只能发起待确认改绑。
2. 改绑**必须**经新通道验证码确认，未确认前账号保持原状。
3. 确认生效后**必须**重置密码；重置前**所有**登录方式一律拒绝（密码 / 邮箱 OTP / 手机 OTP / 社交 / SSO），避免绕过。
4. 2FA 状态与备份码**不因本流程改变**；不提供管理员 2FA 重置（D4）。
5. 管理员**不得**代设密码；重置只能由用户在确认页 / 重置页完成。
6. 全流程审计；旧通道可投递时发送通知，投递失败记录原因。

### 5.3 验证码与令牌

- 统一使用 6 位数字验证码（邮件 / 短信一致），有效期 10 分钟、最多 3 次尝试，与现有 OTP 规格一致。
- 确认页链接只携带不透明请求 ID，用于预填；**令牌消费只发生在 POST**，避免邮件网关预取（沿用阶段 5 的链接安全口径）。
- 请求过期、已验证、已取消均不可重放；同一用户同一通道同时只保留一条有效请求。

### 5.4 「假通道」判定

- 前端展示可操作入口、后端返回成功，但用户实际收不到验证码 / 通知 → 必须在本阶段消除（补实现或隐藏入口 + 明确错误）。
- 失败可区分：`CHANNEL_NOT_CONFIGURED`、`SEND_FAILED`、`TARGET_TAKEN`、`CODE_INVALID`、`CODE_EXPIRED`、`PASSWORD_RESET_REQUIRED`。错误码进入共享口径，文案走语言包。

### 5.5 2FA 覆盖边界（文档口径）

- 只澄清现状：邮箱 OTP、手机 OTP、魔法链接、邮箱验证链接自动登录、社交 / SSO 登录**不触发** 2FA。
- 不在代码层收紧；收紧属阶段 4，且必须晚于阶段 2 / 3。

### 5.6 回滚

- 每条修复按条回退；M8 引入的表与用户字段保留空值即可回退实现，不删列。
- M11 的登录拦截由「必须重置」标记驱动，人工清除标记即可恢复（管理端不提供该操作，运维脚本除外）。
- M4 只在部署方启用短信时真实发送，不改未配置环境的默认行为。

## 6. 依赖与风险

| 项 | 说明 | 缓解 |
| :--- | :--- | :--- |
| 鉴权面改动 | 改的是登录 / 找回 / 管理端写操作 | 审计按 `deep` 执行；每条改动附失败用例 |
| 管理员可发起改绑 | 若管理员同时控制新通道，可借此接管账号 | 仅管理员可发起、必填原因、全流程审计、旧通道通知、`/admin/*` 限流；审批留后续评估 |
| 强制重置拦截 | 拦截过宽会锁死正常用户 | 只拦「必须重置」标记；重置页与找回页始终放行；标记清除路径有测试 |
| 2FA 不重置 | 丢失 2FA + 备份码的用户无自助路径 | 明确告知（D4）；文案与文档写清，不做隐性兜底 |
| 手机通道 | 短信未配置时手机改绑不可用 | 未配置即禁用入口并返回 `CHANNEL_NOT_CONFIGURED`；手机流程依赖 M4 |
| 确认页安全 | 邮件网关预取、链接重放 | 链接只预填、POST 消费；一次性 + 过期 + 尝试次数限制 |
| 上游限制 | `changeEmail` 需旧邮箱确认、`twoFactor` 无管理员重置 | 本阶段走自建受控端点，不依赖上游这两项能力 |
| 数据模型 | 新增 1 个用户布尔字段 + 1 张待确认请求表 | 三方言兼容；生产 ALTER 说明随迁移提交 |
