# 2026-11-21 阶段 10 范围登记：用户侧替代证明（恢复码 / 已验证手机 / 冷静期）

## 1. 目标

- 旧邮箱失效但仍持有恢复因子（恢复码 / 已验证手机 / TOTP / 备份码）的用户，可用「密码 + 第二因子」自助把已验证邮箱换成新邮箱；无任何恢复因子时仍拒绝并引导人工工单。
- 换邮箱进入冷静期（默认 24h，上限 72h），期间可撤销并向新旧邮箱通知；生效后旧邮箱立即失效、不再能登录。
- OAuth-only 用户（无密码）可通过受控自助设置密码进入自助恢复（L0 扩展），避免「社交渠道失效即死锁」。

## 5. 执行顺序

M1 → M2 → M3 → M4 → M5。

先有恢复码才能校验替代证明；证明校验先于改邮箱端点；冷静期依赖请求模型扩展；生效语义必须最后收（否则 pending 期登录语义不清）；界面与测试随各条目附带，M5 收口。

## 6. 不做什么

- 不做设计草案阶段 4「收紧 2FA 覆盖」（邮箱 OTP / 魔法链接 / 社交登录强制第二因子）。
- 不做管理员重置 2FA / 备份码（D4）、管理员代设密码（D8）。
- 不做管理员协助恢复的审批流 / 工单（设计草案阶段 2 剩余）。
- 不做审计检索界面（`GET /admin/audit` 查询面）。
- 不把社交账号列为恢复因子（D6）；不做可信设备列表、passkey、恢复码轮换提醒（设计草案阶段 5）。
- 不引入 Redis 或跨实例限流存储；本期沿用进程内限流，多实例缺口继续留在 backlog。
- 不改 `middleware/auth.global.ts` 的既有白名单语义（除新增页面的精确路径）。
- 不改变阶段 9 管理员改绑的即时生效与强制重置语义；但 `POST /api/channel-change/[id]` 必须新增来源门禁，拒绝用户自助发起的请求（否则可绕过冷静期并触发强制重置）。

## 7. 风险与缓解

| 风险 | 缓解 |
| :--- | :--- |
| 恢复码泄露等同账号接管 | 一次性展示、哈希存储、使用即失效并重签、双通道通知、结构化审计 |
| 手机 OTP 用于设密码导致 SIM swap 提权 | 自助设密码的第二因子集合排除手机 OTP（恢复码 / TOTP / 备份码） |
| 短信 SIM swap | 手机仅用于改邮箱 / 关 2FA，叠加冷静期、通知与限流；服务层拒绝其作为设密码因子 |
| pending 期登录语义歧义 | 冷静期内不改登录标识；生效判定统一走一个纯函数，登录 / 敏感操作 / 请求查询共用 |
| 无后台任务导致到期漂移 | 惰性生效：登录（任意通道）与状态查询读路径判定到期即生效；不活跃用户的漂移上限 = 下次登录（登录本身触发 apply），可接受 |
| OAuth-only 设密码成为新攻击面 | fresh session（15 分钟内登录）+ 第二因子 + 审计 + 不允许在冷静期内设置 |
| 新邮箱输入错误造成二次锁死 | 新邮箱必须完成归属验证才进入冷静期，失败不计入尝试 |

## 8. 验收总则

- 旧邮箱不可投递 + 持有恢复码或已验证手机 → 可自助完成换邮箱，含冷静期撤销。
- 无恢复因子 → 明确拒绝（`PROOF_REQUIRED`），并给出人工工单指引。
- 自助设置密码只接受恢复码 / TOTP / 备份码；手机 OTP 仅用于改邮箱与关闭 2FA。
- 生效后：`email` 覆写为新邮箱（单列模型，不置空）、`emailVerified=true`，旧邮箱不能登录、不能作为标识；全部会话撤销。
- 恢复码使用后立即失效、剩余数量递减；重签是用户显式动作（安全页），不做自动补发。
- 审计覆盖：证明校验、改邮箱申请、撤销、生效、恢复码生成 / 使用 / 轮换、自助设密码。
- 5 语文案键齐全；视觉基线覆盖安全页与换邮箱弹窗（桌面 / 移动 / 暗色）；全量门禁通过。

## 9. 回滚

- M1 / M2 / M3 端点与页面按条回退；新增表 / 列保留（TypeORM 增量同步，不影响旧数据）。
- 冷静期配置回滚为 0 等价「立即生效」，仅在回滚场景使用，不作默认。
- 已生效的换邮箱不回改；撤销只对 pending 请求有效。
