# 2026-11-18 账号找回与 2FA 边界设计草案

> **状态**：草案（2026-11-18）。阶段 0–1 随阶段 9 交付、阶段 3 随阶段 10 交付；阶段 4 已由阶段 11 承接（2026-11-21 登记，尚未开工）；阶段 2 剩余（审批流 / 工单）与阶段 5 仍为候选。后续裁定以各阶段范围登记为准。
> **范围**：登录后的账号恢复、邮箱变更、2FA 重置与人工兜底；覆盖 Web 端、管理端、邮件 / 短信通道。
> **非目标**：本文不实现代码；不改动 OIDC / SSO 协议语义；不评价第三方身份源自身的安全策略。
> **前置调研**：[主流平台账号找回与改邮箱机制调研](./2026-11-18-account-recovery-research.md)。
> **事实源**：`lib/auth.ts`、`components/profile/dialogs/edit-email-dialog.vue`、`components/admin/users/user-detail-dialog.vue`、`utils/shared/env.ts`、better-auth 1.7.20 上游实现。

## 1. 背景

用户邮箱被服务商封禁后，关联账号的可恢复性取决于平台把“邮箱”放在什么位置。按“改邮箱的证明”与“能否绕过 2FA”两个维度，外部平台大致分为 6 类（用户观察），本项目当前落在 **类型 5**：能登录，但改已验证邮箱需要旧邮箱确认。

需要先纠正一个常见前提：**“密码 + 2FA 登录成功”不等于“可以改邮箱”**。当前 `changeEmail` 在 `emailVerified=true` 时，确认信只发往旧邮箱；2FA 不参与该流程。因此 2FA 解决的是“邮箱失效时还能不能登录”，不解决“邮箱失效后能不能换邮箱”。

本文的目标不是立刻改行为，而是把现状、威胁、目标模型与分期路径固定下来，供后续阶段逐条评审、逐条放行。

### 2.2 改邮箱的两条路径

| 当前邮箱状态 | 证明要求 | 结果 |
| :--- | :--- | :--- |
| `emailVerified=true` | 旧邮箱点确认链接 → 新邮箱再验证 | 双邮箱都必须可用；这是**类型 5** |
| `emailVerified=false` | 仅新邮箱验证 | 旧邮箱失效不影响；改完仍为未验证，需要再验证一次 |

- 证据：`lib/auth.ts:216-222`；上游 `better-auth/dist/api/routes/update-user.mjs:445-518`；`email-verification.mjs:200-239`。
- 目标邮箱已被占用时，上游静默返回 `{ status: true }`、不发送任何邮件；前端 `edit-email-dialog.vue:100-117` 不检查 `error`，仍提示“已发送到当前邮箱”。

### 2.5 失效或半失效通道

- **短信重置密码**：`/phone-number/request-password-reset` 只在配置了 `sendPasswordResetOTP` 时发短信；`lib/auth.ts:337-356` 未配置，接口仍返回 `{ status: true }`，前端提示“已发送”。
- **添加密码**：`/set-password` 为 `serverOnly`，OAuth-only 用户无法自助添加密码；只能走“邮箱验证码重置密码”反向创建 credential 账号。
- **备份码再生成**：`/two-factor/generate-backup-codes` 未接 UI。
- **静默失败**：改邮箱不检查 `{ error }`（backlog 已登记）；2FA OTP 发送失败无提示。

### 2.6 会话与敏感操作

- 会话 30 天、`freshAge` 1 天、`updateAge` 1 天（`lib/auth.ts:267-278`）。
- `sensitiveSessionMiddleware` 只校验“会话在数据库中存在”，**不校验新鲜度**（上游 `api/routes/session.mjs:304-311`）；`freshAge` 只用于 `unlink-account`、`list-sessions`。
- 绑定社交（`/link-social`）只需有效会话，且 `allowDifferentEmails: true`；绑定/换绑手机（`phoneNumber.verify({ updatePhoneNumber: true })`）也只需有效会话 + 自己手机的短信。
- 密码重置默认**不撤销**已有会话（上游 `utils/password.mjs:31-46`；未配置 `revokeSessionsOnPasswordReset`），也不会发送安全通知。

| 级别 | 问题 | 后果 | 对应阶段 |
| :--- | :--- | :--- | :--- |
| P0 | 邮箱是事实上的根凭据，2FA 不覆盖邮箱 OTP / 手机 OTP / 社交 / 验证链接 | 邮箱接管 = 全账号接管；2FA 只防“密码泄露但邮箱未泄” | 阶段 3 / 4 |
| P0 | 已验证邮箱改绑依赖旧邮箱确认 | 邮箱失效即类型 5 卡死，2FA 不能解除 | 阶段 3 |

| P2 | 改邮箱 / 改绑静默失败 | 用户误判为成功，错过止损窗口 | 阶段 1 |

## 3. 威胁模型

### 3.1 资产

1. 账号控制权：登录、改密码、改邮箱、关闭 2FA、换绑通道。
2. 邮箱标识：对外可见的 `email`、OIDC `email` claim、系统通知地址。
3. 关联信任：已绑定的第三方账号、OAuth 客户端、SSO 身份源。
4. 历史数据与授权关系。

### 3.2 攻击者能力

| 编号 | 能力 | 典型来源 |
| :--- | :--- | :--- |
| A1 | 邮箱接管（可收信） | 邮箱弱密码、恢复邮箱被攻破、服务商侧劫持 |
| A2 | 会话窃取 | XSS、恶意扩展、共享设备、Cookie 泄露 |
| A3 | 密码泄露 | 撞库、钓鱼、复用密码 |
| A4 | 设备丢失 | TOTP 设备、备份码文件 |
| A5 | 恶意绑定 | 会话被盗后绑定攻击者社交 / 手机 |
| A6 | 内部人员越权 | 管理员权限滥用 |

### 3.3 合法用户故障

| 编号 | 故障 | 当前结果 |
| :--- | :--- | :--- |
| F1 | 邮箱服务商封禁 | 邮箱 OTP / 重置 / 改邮箱全部失效 |
| F2 | 企业邮箱回收（离职） | 同上 |
| F3 | 域名过期、地址被回收 | 同上，且可能被他人重新注册 |
| F4 | TOTP 设备 + 备份码丢失 | 只有密码类登录时无法自救 |
| F5 | 长期未登录、会话过期 | 回到 F1 / F4 的组合 |
| F6 | 唯一登录渠道（社交）失效 | 无其他凭据即丢失 |

### 3.4 设计目标

- **G1 可恢复**：每种常见故障至少有一条自助路径；没有自助路径时必须有人工路径。
- **G2 抗接管**：任何单一因子（邮箱、密码、会话）都不得单独完成根凭据变更。
- **G3 可挽回**：改绑 / 恢复后有时间窗撤销，并向用户发送通知。
- **G4 可审计**：所有自助与人工恢复事件可追溯（谁、何时、改了什么、依据是什么）。
- **G5 不降低现有安全性**：默认配置不弱于当前；新路径可配置关闭。

### 3.5 非目标

- 不做 KYC 级身份证明或线下核验。
- 不强制硬件安全密钥。
- 不引入第三方身份验证服务。
- 不改变 OIDC 的 `sub` 稳定性与现有客户端契约。

## 4. 设计原则

1. **恢复强度 ≥ 登录强度**：恢复本质上是另一种认证，不能比正常登录更弱（OWASP）；NIST 要求恢复方法基于风险评估并记录选择理由。
2. **多根而非单根**：邮箱、TOTP / 恢复码、已验证手机、可信设备、已绑定社交都是通道；任一“密码 + 因子”组合应可用，但单一通道不得成为唯一根。
3. **根凭据变更需要两个独立证明 + 通知 + 冷静期**：证明可以是旧邮箱、TOTP、恢复码、已验证手机、可信设备或人工复核。
4. **恢复事件必须可检测、可撤销**：通知旧 / 新通道，冷静期内可取消；使用恢复码后立即失效并重新签发。
5. **人工兜底是最后一道，不是第一道**：管理端能力必须有，但不能成为唯一路径。
6. **默认安全、显式配置**：新路径默认关闭或默认保守，由部署方按用户群选择。
7. **不把“邮箱可用”作为唯一前提**：这是当前设计最大的结构性风险。

## 5. 目标模型（建议）

### 5.1 术语

- **登录因子**：密码、邮箱 OTP、手机 OTP、社交 OAuth、SSO、魔法链接。
- **恢复因子**：TOTP、备份码、恢复码、已验证手机、可信设备、人工复核。
- **根凭据**：邮箱地址、密码、2FA 注册状态、已绑定的登录通道。
- **恢复等级**：按证明强度分层，而不是按具体通道绑定。

### 5.2 恢复等级与操作矩阵

| 等级 | 最低证明 | 允许的操作 |
| :--- | :--- | :--- |
| R0 | 任一登录因子（邮箱 OTP / 手机 OTP / 社交 / 密码） | 登录、查看资料 |
| R1 | 密码 + 邮箱或手机 OTP | 修改密码、补绑手机 / 社交 |
| R2 | 密码 + 第二因子（TOTP / 备份码 / 恢复码 / 已验证手机） | 修改已验证邮箱、关闭 2FA、解绑通道 |
| R3 | 人工工单 + 管理员复核 + 审计 | 重置 2FA、极端找回、争议账号处置 |

> 说明：R2 的核心是“两个独立因子”，不强制“旧邮箱”。旧邮箱只是可用证明之一，不再作为唯一证明。OAuth-only 或手机注册用户若要使用 R2，需要先有密码；当前 `/set-password` 为 `serverOnly`，阶段 3 需提供受控的自助设置密码端点（要求 fresh session + 第二因子）。

### 5.3 恢复路径决策树

| 用户状态 | 推荐路径 | 目标结果 |
| :--- | :--- | :--- |
| 邮箱可用 | 邮箱 OTP 登录 / 重置（R0 / R1） | 完全可恢复 |
| 邮箱不可用，记得密码，有 TOTP / 恢复码 | 密码 + 第二因子 → R2 改邮箱 | 可自助换邮箱 |
| 邮箱不可用，记得密码，有已验证手机 | 密码 + 短信 OTP → R2 改邮箱 | 可自助换邮箱（短信风险单独评估） |
| 邮箱不可用，忘记密码，有已验证手机 | 手机 OTP 登录 → 设置新密码 → R2 | 可自助恢复 |
| 邮箱不可用，仅有密码类登录，无第二因子 | 人工工单（R3） | 需要管理员兜底 |
| 唯一社交渠道失效，无其他凭据 | 人工工单（R3） | 需要管理员兜底 |
| 匿名账号 | 无找回 | 明确告知“会话丢失即丢” |

### 5.4 冷静期与通知

- **改邮箱**：提交后进入 `pending`，默认 24–72 小时生效；期间向旧邮箱（若可投递）与新邮箱发送通知，旧设备可撤销；生效后旧邮箱不再能用于登录。
- **关闭 2FA / 换绑通道**：立即生效或短冷静期（建议 24 小时），同时通知全部已登记通道。
- **使用恢复码**：立即失效并重新签发一组；触发恢复通知（NIST SP 800-63B-4 §4.2）。
- **通知失败**：记录失败原因并在管理端可见，不能静默；必要时回落到其他已登记通道。

## 6. 分阶段路线

> 原则：**先修事实、再补人工、再做替代证明、最后收紧 2FA**。顺序反了会制造更多死锁。

### 阶段 0：基线与可观测性（不改行为）

- 为改邮箱、2FA 开关、密码重置、社交 / 手机绑定补结构化审计：操作人、目标用户、before / after、来源 IP / UA、工单号、结果。
- 为上述路径补集成测试与失败用例（含“旧邮箱失效”“目标邮箱已占用”“SMTP 失败”）。
- 同步文档：修正用户文档中“短信 / 邮箱验证码属于 2FA 方法”的表述，明确哪些通道不触发 2FA。
- **退出条件**：审计可查、关键路径有测试、文档与代码一致。
- **风险**：低；主要是日志量与测试成本。

### 阶段 1：修复“看起来有、实际没有”的通道（低风险）

- 配置 `sendPasswordResetOTP`，或在未配置时隐藏短信重置入口并返回明确错误。
- 备份码支持重新生成（接 `/two-factor/generate-backup-codes`）。
- 2FA 邮件 OTP 发送失败时回落短信，并向用户明确提示“已发送 / 发送失败”。
- 改邮箱、改绑、撤销会话等流程补 `{ error }` 检查；目标邮箱已占用时给出明确提示。
- 管理员改密码改调 `/admin/set-user-password`。
- **退出条件**：每条通道都有成功 / 失败用例，不存在“提示成功但实际未发送”。
- **回滚**：按条回退；不改数据模型。

### 阶段 2：人工兜底与管理端闭环

- 管理员重置 2FA（删除 `two_factor` 行并复位 `user.twoFactorEnabled`），要求二次确认、原因、工单号，并通知用户。
- 管理员改邮箱、设置密码使用正确入口；改邮箱后保持 `emailVerified` 语义清晰。
- 管理端展示用户的登录通道、2FA 状态、最近恢复事件。
- **退出条件**：被锁账号可在 10 分钟内人工恢复，审计完整；误操作可回滚。
- **风险**：管理员权限集中；需要审批与审计双保险。

### 阶段 3：用户侧替代证明（核心，2026-11-21 已随阶段 10 交付）

- 引入“恢复码”（独立于 2FA 备份码，或明确复用备份码；≥ 64 bit、哈希存储、一次性、可轮换）。
- 允许“密码 + 恢复码 / 已验证手机”修改已验证邮箱，替代旧邮箱确认。
- 改邮箱进入冷静期，支持撤销与通知；生效后旧邮箱失效。
- **退出条件**：旧邮箱失效但有恢复因子的用户可自助换邮箱；无恢复因子仍被拒。
- **风险**：恢复码泄露 = 账号泄露；需要一次性展示、离线保存提示、使用通知与轮换。
- **落地口径（2026-11-21，阶段 10）**：D2 定为**独立恢复码**（不复用备份码）；手机 OTP 只用于改邮箱 / 关 2FA，不用于设置密码（D3 延伸）；冷静期默认 24h、上限 72h（D5）；生效后旧邮箱立即失效（D7）。实现见 `server/utils/recovery-code.ts`、`server/utils/recovery-proof.ts`、`server/utils/channel-change-state.ts`、`server/utils/channel-change-apply.ts`；唯一口径已回写 [安全规范 §1.3](../../standards/security.md#13-2fa-覆盖边界与账号恢复等级-2fa-coverage--recovery-levels)。设计草案中的 `R0–R3` 仅作参照代号，落地统一映射到 `L0–L2`。

### 阶段 4：收紧 2FA 覆盖（已由阶段 11 承接，2026-11-21 登记）

- 让邮箱 OTP、手机 OTP、魔法链接、邮箱验证码 / 邮箱验证链接自动登录、社交与 SSO 登录在 `twoFactorEnabled` 时也要求第二因子。
- **前置条件**：阶段 2 / 3 已上线，否则“邮箱失效 + 设备丢失”会变成真正的死锁。
    > **裁定（2026-11-21）**：「管理端重置 2FA」已被 D4 永久排除，阶段 2 剩余审批流 / 工单不构成本阶段前置；阶段 3 随阶段 10 交付、管理员协助恢复随阶段 9 交付，按「用户侧恢复已具备」判定前置满足。L2（同时丢失 2FA 与备份码）为已接受边界。详见 [阶段 11 范围登记](./2026-11-21-phase11-registration.md) §2 / §8。
- **退出条件**：开启 2FA 后所有登录通道都要求第二因子；恢复路径仍可用；有灰度与回滚开关。
- **风险**：可用性下降、用户投诉；需要产品与客服预案。

### 阶段 5：长期演进

- 可信设备列表与吊销、恢复事件告警、风险评分、恢复码轮换提醒。
- 评估 passkey / 硬件密钥作为恢复因子。
- 评估多实例下的限流与审计存储。

| D2 | 恢复码与 2FA 备份码 | 合并 / 分离 | 分离：恢复码用于“通道全失”场景，语义更清晰；若成本高可先复用备份码并改名 |

## 8. 兼容性与影响面

### 8.1 上游限制

- `changeEmail` 没有“替代证明”参数；需要在 Nitro 侧新增受控端点：先校验恢复因子与冷静期状态，再调用上游或直接更新用户 + 发验证邮件。
- `twoFactor` 没有管理员重置端点；需要自建 admin API，删除 `two_factor` 行、复位 `user.twoFactorEnabled`，并写审计。
- `/set-password` 为 `serverOnly`；管理员改密码应使用 `/admin/set-user-password`，或服务端调用 `auth.api.setPassword`。
- 2FA 的触发范围由上游 `signInPaths` 决定；收紧覆盖需要在上游 hook 之外增加自定义中间件或等待上游能力。

### 8.2 数据与迁移

- 新增恢复码字段或独立表（哈希、创建时间、使用时间、失效时间）。
- 新增恢复事件 / 审计表（操作类型、目标、before / after、来源、工单号、结果）。
- 新增改邮箱 `pending` 状态（或独立表）与冷静期字段。
- 迁移需兼容 SQLite / MySQL / PostgreSQL。

### 8.3 前端与文案

- `profile` 改邮箱对话框：区分“旧邮箱可用 / 不可用”两条路径；展示冷静期与撤销入口。
- `security`：备份码 / 恢复码再生成、2FA 重置说明、可信设备列表。
- `admin/users`：2FA 状态、恢复事件、重置入口、工单字段。
- 新增 i18n 键、邮件模板（改邮箱通知、恢复通知、冷静期生效通知）；`admin/users` 移除「新密码」输入，改为「发送重置邮件」动作（D8）。
- 视觉基线覆盖 profile / security / admin 的相关弹窗与状态。

### 8.4 API 与集成方

- 新增 admin 端点需进入 OpenAPI 与 API 文档。
- 邮箱变更不影响 OIDC `sub`；`email` claim 会变化，需在变更生效后通知依赖方或等待下次授权刷新。
- SSO / OAuth 客户端不受影响，但依赖 `email` 做账号匹配的集成方需要知悉。

## 9. 验收标准（总）

1. 任一常见故障场景都有明确路径（自助或人工），并有测试覆盖。
2. 任何单一因子都不能完成根凭据变更。
3. 所有恢复 / 改绑事件有审计与通知，且可在冷静期内撤销。
4. 默认配置不弱于当前；新路径可配置关闭。
5. 文档、i18n、API、测试、视觉基线同步。

## 10. 开放问题

- 是否接受“恢复码丢失 = 永久丢失”（GitHub / Apple 模式）？如果接受，需要在启用时明确告知。
- 是否有客服 / 工单系统？没有的话，管理员兜底的“工单号”如何落地（Issue、外部系统或备注）？
- 管理员是否应看到用户的 2FA 密钥？建议只看到状态，不显示密钥。
- 旧邮箱不可投递时，通知失败如何在 UI 上表达，避免用户误以为“已通知”？
- 迁移期如何避免“用户以为已生效但实际在冷静期”的困惑？需要明确的邮件与页面文案。
