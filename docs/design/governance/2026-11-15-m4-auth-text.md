**视觉基线重采归因（第 3 轮修正）**

第 1 轮把暗色表面色漂移写成 M4-2 引入，第 2 轮又把这批差异写成「切换器 + 文案节点拆分的字形位移」，两次都不准确。逐像素核对后的结论：

1. **漂移是主题 token 的换代，早于 M4-2**。旧基线与当前构建的差异只有 4 组 token 颜色（桌面图逐像素统计，这三组的计数在三张图上完全一致；余下差异是同一组 token 在抗锯齿边缘的残差）：

    | 旧值 → 新值 | `about-dark-desktop` | `register-dark-desktop` | 含义 |
    | :--- | ---: | ---: | :--- |
    | `rgb(24,24,27)` → `rgb(30,30,30)` | 2,738 | 48,498 | 表面色 `#18181b` → `--admin-surface` `#1e1e1e` |
    | `rgb(63,63,70)` → `rgb(55,65,81)` | 130 | 130 | 边框 `--admin-border` |
    | `rgb(153,153,154)` → `rgb(156,156,156)` | 32 | 32 | 弱化文本 |
    | `rgb(255,107,107)` → `rgb(230,57,70)` | 23 | 23 | 品牌红 `#e63946` |

   `about` 只差切换器（2,738 px）；`register` / `forgot-password` 的表面色差异高达 48,498 / 34,788 px，是因为该基线记录的是迁移前 PrimeVue 输入框底色，`auth` 表单控件迁到 caomei-ui + 项目暗色 token 后整片刷成 `#1e1e1e`（P5-1 `f91e6e4` 起，切换器也由 `--p-content-background` 改为 `--admin-surface`）。**没有任何字形位移**：差异像素中 99% 是纯色替换，其余是同一组 token 在抗锯齿边缘的残差。

2. **门禁为什么一路绿灯**：`visualExpect.threshold: 0.2` 对应 pixelmatch 的单像素上限 `35215 × 0.2² ≈ 1,408.6`，而这批差异的最大单像素 delta 只有 **902.4**（`24,24,27 → 30,30,30` 仅 16.6）。低于阈值的像素被判定为「相同」，**不计入** `maxDiffPixels: 200`，所以「4.8 万像素不同」与「200 像素上限」并不矛盾——这正是纯色漂移能长期潜伏的机制。

3. **重采模式只补失败项**：`test:visual:update` 传的是裸 `--update-snapshots`，Playwright 默认语义是 `changed`，只重写比对失败的快照。M4-2 首次回归的 19 张失败来自真实文案位移（每张越阈像素 676–14,078，均远超 `maxDiffPixels: 200`），重写这 19 张时顺带写入了新的表面色；`register` / `forgot-password` 没有越阈值的位移，从未被重写，集合内部才会同时存在两种渲染。

4. **复核证据**：固定容器（`mcr.microsoft.com/playwright:v1.65.0-noble`）内启动同一份 `.output`，5 个认证页在 `html.dark` 下 `--admin-surface` 计算值为 `#1e1e1e`，`.language-switcher__trigger` 背景 `rgb(30, 30, 30)`；`/quick-login` 手机号 Tab 标签在 zh / en 下分别为「手机号」「Phone number」。

5. **本轮处理**：对 5 个认证页的暗色状态改用 `--update-snapshots=all` 强制重采，并顺带重采 `about` / `privacy` / `terms`。共 11 张变更：

| 基线 | 差异像素 | 差异包围盒 | 归因 |
| :--- | ---: | :--- | :--- |
| `about-dark-*` / `privacy-dark-*` / `terms-dark-*`（6 张） | 3,379 | 仅切换器矩形 | 主题 token 漂移（切换器） |
| `register-dark-{desktop,mobile}` | 49,311 / 37,209 | 卡片 + 切换器 | 主题 token 漂移（切换器 + 表单控件底色 / 边框） |
| `forgot-password-dark-{desktop,mobile}` | 35,469 / 27,241 | 卡片 + 切换器 | 同上 |
| `quick-login-light-desktop-tab-phone` | 36,490 | 手机号字段标签 | RG-B1 缺键修复后由「`auth.quick.fieldPhone`」恢复为「手机号」 |

`login` / `change-password` / `quick-login` 的暗色基线在 `dc74f4c` 已按当前构建重采，本轮强制重采后与旧基线字节一致，可反证构建稳定。`sso-login` / `security` 的暗色基线仍带同类亚阈值漂移（不在 M4 范围，未做归因），已登记 backlog「视觉基线对低于阈值的纯色漂移无感」。

> 关于「verify 可能比对到非同代构建」：`scripts/testing/run-visual.mjs` 每次都在同一次容器调用里串行执行 `pnpm i --frozen-lockfile && pnpm build && pnpm <layer>`，`webServer` 也是本进程新建的，不存在复用旧 `.output` 的路径；绿灯的成因是第 2 条的阈值机制与第 3 条的增量重采，而不是构建陈旧。为便于审计，产物 SHA / 提交号的打印已登记到同一 backlog 条目。

## 6. 已知边界

- `utils/**` 不在硬编码扫描目标内，`utils/shared/password*` 的残留中文属扫描盲区；M4-2 切换页面后删除旧函数，M17 再评估是否把「产出用户可见文案的 utils」纳入扫描。
- 表单内联错误与验证码错误在赋值时固化为当前语言；`setLocale()` 原地切换后已显示的文本不会刷新（Toast 瞬时无影响），与组件库内建文案口径一致，M4-2 验证时按此边界记录。
- `getFirstZodError` 的兜底统一为 `auth.common.validationFailed`，避免 Zod issue 缺失时「点击提交无反馈」。
- `i18n:check` 目前不校验「源码 `t('...')` 的键在语言包中存在」，`auth.quick.fieldPhone` 缺键因此在全绿门禁下漏到生产构建；反向键校验已登记 backlog。
