# 国际化实施方案 (i18n Implementation Plan)

本文档规划草梅 Auth 项目的国际化落地路径，参考墨梅博客（momei）已验证的 i18n 治理体系，并适配本项目现有代码基础（`utils/shared/locale.ts`、`server/utils/locale.ts`、better-auth 生态）。目标是建立可扩展、可维护的多语言能力，为前端、服务端、模板与运营内容提供统一的翻译能力。

> **状态**：`proposal`（M1 技术验证已完成，阶段 2 M5 于 2026-11-06 归档；**M2 前置与服务端错误消息试点已随阶段 3 授权**，见 [阶段 3 登记记录](../design/governance/2026-11-06-phase3-registration.md)；页面文案翻译（M2）与邮件 / `User.locale`（M4）仍未授权）。已引入 `@nuxtjs/i18n` 与 Locale Registry、语言切换原型，但无业务文案翻译；网页 UI、Meta、MJML 邮件与 API 错误消息仍以简体中文硬编码为主。现有 `better-auth-localization` 仅覆盖认证插件边界，`utils/shared/locale.ts` 与 `server/utils/locale.ts` 提供 locale 检测。候选登记见 [backlog §1.1](../plan/backlog.md#11-i18n-全量落地)。
>
> **2026-11-05 复核**：技术版本、模块化加载、Zod v4 错误本地化、服务端 `useTranslation`、邮件用户偏好与组件库迁移顺序已修订。详细评估与证据见 [i18n 评估与实施方案](../design/governance/2026-11-05-i18n-evaluation.md)；本规范保留为执行口径，评估文档保留取证与取舍理由。

## 1. 现状与目标

### 1.1 现状

-   `nuxt.config.ts` 未引入 i18n 模块，`head.htmlAttrs.lang` 与 PrimeVue locale 硬编码为中文（`locale: zh_CN`）。
-   `utils/shared/locale.ts` 定义了 `SUPPORTED_LOCALES`（当前为 `zh-Hans` / `zh-Hant` / `default` 等 better-auth 风格标识）与 `server/utils/locale.ts` 完整语言检测工具（Cookie / Header / Accept-Language 优先级检测）。
-   网页 UI、Meta 信息、邮件模板（MJML）大多为简体中文硬编码。
-   服务端 API 响应、错误消息、日志没有统一翻译策略。

### 1.2 目标

1. 支持至少 `zh-CN` 与 `en-US` 两个语言包，并为未来语言扩展留接口。
2. 所有用户可见文本（Web、Email、验证错误、通知）都可基于 locale 切换。
3. 保持 SSR、SEO 以及 Demo 模式兼容。
4. 建立翻译交付流程与质量保障机制（审计脚本 + 测试门禁）。

## 2. 语言标识规范（重点）

**项目内部统一采用与 PrimeVue / Nuxt i18n 对齐的区域码标识作为唯一业务规范**：

- `zh-CN`（简体中文，默认语言）
- `en-US`（英语）

规范要求：

1. `i18n/locales/<locale>/` 目录名必须使用这套标识。
2. 页面路由、语言切换、SEO、服务端翻译装配都必须以这套标识为准。
3. **`better-auth-localization` 使用的 `zh-Hans`、`zh-Hant`、`default` 仅作为认证插件边界适配值存在，不能反向成为项目内部标准。**

**迁移说明**：当前 `utils/shared/locale.ts` 与 `server/utils/locale.ts` 使用的是 better-auth 风格标识（`zh-Hans` / `zh-Hant` / `default`）。规划落地时，认证层负责把 better-auth 的 locale 标识映射回项目内部 locale（`zh-Hans` → `zh-CN`、`zh-Hant` → `zh-CN` 或后续 `zh-TW`、`default` → `en-US`），业务层不跟随认证插件的命名体系。

## 3. 技术选型

| 层面 | 推荐技术 | 说明 |
| --- | --- | --- |
| 前端 UI | `@nuxtjs/i18n` **v10**（当前 10.6.0，支持 Nuxt 4） | 集成 `vue-i18n` 11.x，支持 SSR、路由前缀、懒加载、SEO；v10 起 `lazy` 选项已移除，语言文件始终懒加载 |
| 语言元数据 | `i18n/config/locale-registry.ts`（Locale Registry） | 统一维护启用语言、默认语言、路由前缀、回退链与就绪度 |
| 模块映射 | `i18n/config/locale-modules.ts` + `locale-runtime-loader.ts` | 定义 module 与 key group、路由按需加载、前后端共享装配 |
| dayjs | 原项目 `dayjs` + 按 locale 动态加载 | 通过插件监听 locale 切换，动态设置 `dayjs.locale` |
| caomei-ui | `CaomeiConfigProvider` + `useLocale`（PrimeVue `locale` / `primelocale` 已在阶段 4 P5 下线） | 组件内建文案必须与应用 locale 同步（详见 [caomei-ui 迁移评估 §8.2](../design/governance/2026-11-05-caomei-ui-migration-evaluation.md)） |
| 表单校验 | Zod v4 **per-parse error map** + 翻译键 | 不使用全局 `z.config(z.locales.*)`（SSR 多请求会串语言）；Schema 内不调用 `t()` |
| 服务器响应 | 共享 Locale Registry + `experimental.localeDetector` + `useTranslation(event)` | 服务端按请求语言装配消息，复用现有 `server/utils/locale.ts` 的语言检测能力 |
| 邮件模板 | MJML 模板参数化 + 语言包 + 用户语言偏好 | 按用户 `locale` 自动切换翻译片段；同步流程可用请求 locale 兜底 |
| 内容管理 | JSON/TS 语言包 + 治理脚本 | `scripts/i18n/` 下审计脚本保证键一致与未翻译项可视化 |

## 4. 目录与命名规范

### 4.1 Locale Registry（规划引入）

```
i18n/
  config/
    locale-registry.ts        # 语言元数据：启用语言、默认语言、回退链、就绪度
    locale-modules.ts         # 模块注册：module 与 key group、路由与按需加载映射
    locale-runtime-loader.ts  # 运行时加载器（前端 lazy + 服务端装配共用）
  locales/
    zh-CN/
      common.json             # 通用文案（导航、按钮、Toast）
      auth.json               # 认证/登录模块
      profile.json            # 个人中心
      security.json           # 密码 / 2FA / 会话
      oauth.json              # OAuth 客户端 / 授权确认
      sso.json                # SSO 登录
      admin.json              # 管理后台（壳层 + 全局菜单）
      admin-users.json        # 后台业务域独立模块
      admin-oauth.json
      admin-sso.json
      admin-logs.json
      demo.json               # Demo 模式虚拟数据文案
      email.json              # 邮件模板文案
      errors.json             # 通用错误
      validation.json         # 表单校验错误键
      server-only.json        # 服务端专用错误 / 通知（可选）
    en-US/
      ...
  localeDetector.ts           # 服务端请求 locale 检测（v10 experimental.localeDetector）
  i18n.config.ts              # vue-i18n datetime / number 格式（Nuxt transform 加载）
  nuxt-i18n.config.ts         # Nuxt 模块层配置（jiti 安全，由 nuxt.config.ts 顶层 import 并 spread）
```

-   Key 命名采用 `域.页面.语义`，例如 `auth.login.title`、`security.mfa.enableButton`。
-   避免在组件内定义语言常量，统一从语言包读取。
-   前后端共用 `common.json` 与 `auth.json`，特殊场景（如日志）使用 `server-only.json`。
-   **单一事实源**：目录、模块、里程碑、脚本与验收口径以本规范为准；[i18n 评估与实施方案](../design/governance/2026-11-05-i18n-evaluation.md) 只保留现状取证、取舍理由与风险，不重复定义执行口径。

### 4.2 后台 locale 拆分策略

-   `admin.json` 只保留后台壳层和全局菜单所需的稳定标题，保证管理员在非后台页面也能预加载基础后台导航文案。
-   各后台业务域拆分为独立 module（如 `admin-users`、`admin-oauth`），沿用既有 `pages.admin.*` key 路径，不要求业务代码改写 `t()` 调用。
-   `i18n/config/locale-modules.ts` 是模块注册的唯一事实源：定义 module 与 key group 的对应关系，以及路由与按需加载 module 的映射。

## 5. 就绪度分级与回退链（参考 momei 治理经验）

新增语言采用"先 `ui-ready`，后 SEO 放量"策略：

| Locale | 路由前缀 | 就绪度 | 回退链 | 可切换 | 可索引 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `zh-CN` | 无（默认） | `seo-ready` | `zh-CN` | 是 | 是 |
| `en-US` | `/en-US` | `ui-ready`（M5 满足门禁后升 `seo-ready`） | `en-US -> zh-CN` | 是 | 否（M5 后升为是） |
| 未来语言 | `/xx-XX` | `ui-ready` 起步 | 按语义就近回退 | 是 | 否（满足门禁后升级） |

说明：

-   `ui-ready` 语言参与前端切换、页面渲染、组件库内建文案同步与服务端翻译装配，但不会被 SEO 视为可索引语种，也不进入 sitemap 与 feed alternates。
-   `ui-ready` 升级到 `seo-ready` 的门禁：全部模块 key parity 通过、审计脚本无缺词、前端关键链路定向测试通过、服务端邮件 locale 覆盖、SEO 输出确认无泄漏；`en-US` 在 M5 满足门禁后升级。

## 6. 实施步骤

### 阶段 A：基础设施

1. 安装依赖：

    ```bash
    pnpm add -D @nuxtjs/i18n
    ```

2. 在 `nuxt.config.ts` 中追加模块与配置（v10；`lazy` 已移除，改用 `files[]`）：

    ```ts
    export default defineNuxtConfig({
        modules: [
            // ...现有模块
            "@nuxtjs/i18n",
        ],
        i18n: {
            defaultLocale: "zh-CN",
            strategy: "prefix_except_default",
            langDir: "locales",
            detectBrowserLanguage: {
                useCookie: true,
                cookieKey: "i18n_locale",
                redirectOn: "root",
            },
            experimental: {
                localeDetector: "localeDetector.ts",
            },
            locales: [
                {
                    code: "zh-CN",
                    language: "zh-CN",
                    name: "简体中文",
                    files: ["zh-CN/common.json", "zh-CN/auth.json"],
                },
                {
                    code: "en-US",
                    language: "en-US",
                    name: "English",
                    files: ["en-US/common.json", "en-US/auth.json"],
                },
            ],
            compilation: { strictMessage: true },
        },
    })
    ```

    > `files[]` 的完整清单由 `i18n/config/locale-modules.ts` 生成，不在 `nuxt.config.ts` 手写第二份；上例只展示形状。

3. 建立 `i18n/config/locale-registry.ts`，集中维护语言元数据（与 momei Locale Registry 同构），并将 `utils/shared/locale.ts` 的 `SupportedLocale` 收敛到项目内部标识。

4. 新增插件 / 组合式监听 locale 变更：组件库内建文案（PrimeVue `primelocale` 或 caomei-ui `CaomeiConfigProvider`）、`dayjs.locale` 动态切换、`useLocaleHead` 渲染 `lang` / `dir` / `hreflang`。

### 阶段 B：页面与组件

1. 扫描 `pages/`、`components/` 中硬编码中文，替换为 `t('...')`。
2. 为布局、导航、按钮等公共组件使用 `common.json`。
3. 输入验证与 Toast 信息调用 i18n。
4. 使用 `<i18n-t>` 处理内嵌 HTML 的文案。
5. 路由级别使用 `defineI18nRoute` 配置多语言路径。

### 阶段 C：第三方库与 SEO

1. 组件内建文案：迁移期按 locale 注入 PrimeVue `primelocale`；组件库迁移完成后删除 `plugins/primevue-i18n`，改接 caomei-ui `CaomeiConfigProvider` + `useLocale`。
2. 引入 `dayjs/locale/zh-cn`、`dayjs/locale/en`，在插件内 `dayjs.locale(currentLocale)`。
3. `useHead`、`useSeoMeta` 多语言处理，OG 标签多语言；sitemap / feed alternates 只输出 `seo-ready` 语种。

### 阶段 D：服务端与模板

1. 使用 v10 的 `experimental.localeDetector`（`i18n/localeDetector.ts`）：
    - 优先级 URL > Cookie `i18n_locale` > 旧 `locale` / `language` / `lang` > `Accept-Language` > 默认。
    - 复用 `server/utils/locale.ts` 的归一化映射与 better-auth 边界映射。
    - 首次命中旧 Cookie 时回写 `i18n_locale`，避免 SSR 读旧 Cookie、客户端只认新 Cookie 造成首帧语言不一致。
2. API handler 使用 `const t = await useTranslation(event)`（服务端专用、experimental），不自行注入 `event.context.t`。
3. 认证层增加 better-auth locale 映射：`zh-Hans` / `zh-Hant` / `default` → 项目内部 locale（`zh-CN` / `en-US`），业务层不接触认证插件命名。
4. MJML 模板静态中文改为变量，渲染时传入 `t`；按用户 `locale` 选择翻译片段。
5. API 错误消息统一走 i18n（`createError({ message: t('errors.auth.invalidCode') })`），响应设置 `Content-Language` 与 `Vary: Accept-Language, Cookie`。
6. 日志保留英文默认值，支持附带语言的业务日志（用于分析）。

### 阶段 D.1：Zod v4 错误本地化

1.  共享 Schema（`utils/shared/validators.ts` / `schemas.ts` / `api-schemas.ts`）中的 74 处 schema 级中文 `message` 移除或改为错误键；标准 issue 交给 error map。
2.  前端 `useForm` 增加 `zodErrorMap` 选项，`safeParse(values, { error: map })`；map 从 `validation.*` 读取。
3.  服务端 `validateBody` / `validateQuery` / `validateParams` 接受 `event`，用 `useTranslation(event)` 生成 map；`getFirstZodError` 返回翻译后的消息。
4.  禁止在 Schema 内调用 `t()`；禁止使用全局 `z.config(z.locales.*)`（SSR 多请求会串语言）。

> **2026-11-09 落地（M5-1）**：`validators.ts` / `schemas.ts` / `api-schemas.ts` 内的中文消息已全部改为 `validation.*` 键，共 76 个键，`zh-CN` / `en-US` 同构（单测强制校验）。边界统一用 `resolveValidationMessage`：组件内经 app 全局 `$t` 翻译，无 i18n 上下文（单测 / 非组件调用）回退 `utils/shared/validation-messages-zh.ts` 的 zh-CN 文案，避免把键暴露给用户。注意：`@nuxtjs/i18n` 会把 locale JSON 编译为消息 AST，shared 代码不能直接 import JSON 取值。

### 阶段 D.2：服务端错误消息试点（M5-3）

**2026-11-09 落地**：认证类 API 的错误消息先走 `errors.*` 键，验证 `useTranslation(event)` 与响应头链路；其余 API 保持原状，后续按里程碑放量。

1.  语言包：`i18n/locales/<locale>/errors.json`，`zh-CN` / `en-US` 同构，已登记到 Locale Registry 的 `files[]`。
2.  服务端工具 `server/utils/i18n.ts`：
    -   `getRequestLocale(event)`：优先级与 `i18n/localeDetector.ts` 一致（query `locale` → `i18n_locale` → 旧 Cookie → `Accept-Language` → 默认）。
    -   `getServerI18n(event)`：调用 `useTranslation(event)`，按 event 缓存；翻译缺失或 `useTranslation` 不可用时回退 `utils/shared/error-messages-zh.ts` 的 zh-CN 文案。
    -   `createLocalizedError(event, { statusCode, key })`：生成带当前语言 `message` 的 `H3Error`。
3.  响应头：`server/middleware/1-i18n.ts` 在认证类 API（`/api/auth`、`/api/oauth`、`/api/sso`、`/api/social`）上设置 `Content-Language` 与 `Vary: Accept-Language, Cookie`，位于鉴权中间件之前，覆盖 401 / 403 / 405 / 429 等错误响应。
4.  试点范围：`get-user-session`、`check-admin`、`rate-limit`、`server/middleware/2-auth.ts`、OAuth 同意 / 撤销 / 客户端信息、SSO Provider 列表、社交登录 Provider 列表。试点内 Zod 校验通过 `createZodErrorMap(t)` + `translate` 翻译标准 issue 与 `validation.*` 自定义消息。
5.  回退登记：`useTranslation` 属 experimental；非认证类路径直接返回 zh-CN 兜底、不加载消息；单测 / 非 HTTP 上下文 / 中间件未初始化时同样回退 zh-CN，不阻塞响应。动态内部错误消息（如数据库驱动原始错误）保持原文，不强制翻译，避免丢失诊断信息。
6.  未纳入本批：Admin API、文件上传、邮件 / 短信模板与其他非认证类端点；随 i18n M4 / M5 放量。

> 验证：`tests/unit/server/i18n-response.spec.ts`、`tests/unit/i18n/error-messages.spec.ts`，以及认证类 API 的定向测试。本地生产构建 smoke：`Accept-Language: en-US` 请求 `/api/sso/providers/available`（405）返回 `Method not allowed`，`/api/oauth/consents`（401）返回 `Unauthorized`；`zh-CN` 分别返回 `方法不允许` / `未登录用户`；两类响应均带 `Content-Language` 与 `Vary: Accept-Language, Cookie`。

### 阶段 E：运营内容 & Demo 模式

1. Demo 模式虚拟数据文案提供多语言版本（`demo.json`）；生成器接受 locale，或明确 Demo 仅 `zh-CN` 并登记。
2. 管理后台列表（如 OAuth 客户端描述）若来自数据库，标注是否支持多语言字段。
3. 未来引入 CMS 时，在语言包中保留占位符或在 API 层做翻译映射。

## 7. 自动化与质量保障

### 7.1 治理脚本（2026-11-09 已落地，参考 momei）

| 脚本 | 职责 | 阻断级别 |
| --- | --- | --- |
| `scripts/i18n/audit-locale-keys.mjs` | 校验 key parity、缺失、未使用、未翻译候选；支持 `--only=` 与 `--fail-on-*` | 缺失 = blocker（带 `--fail-on-missing`）；未使用 / 未翻译 = warning |
| `scripts/i18n/check-locale-parity.mjs` | 语言目录、模块文件、key 结构与值类型一致 | blocker |
| `scripts/i18n/audit-duplicate-messages.mjs` | 默认语言内完全相同的文案候选 | warning |
| `scripts/i18n/audit-hardcoded-text.mjs` | 扫描 Vue 模板、composables、服务端 API / 工具与 MJML 模板中的中文硬编码 | 基线外新增 = blocker；可收紧项 = warning |
| `scripts/i18n/check-locale-fallback.mjs` | 校验 Registry 的默认语言、回退链、路由前缀、就绪度、`indexable` 与 `files[]` 完整性 | blocker |

脚本共用 `scripts/i18n/lib/`：

-   `locale-data.mjs`：加载 Registry（Node 原生类型擦除直接导入 `.ts`）、读取 / 拍平语言包、键差异、源码键引用扫描。
-   `registry-rules.mjs`：Registry 规则校验（纯函数，单测覆盖）。
-   `hardcoded-scan.mjs`：硬编码中文扫描与基线比较（纯函数，单测覆盖）。

审计口径：

-   **未使用键**：只在应用运行时目录（`app.vue`、`pages`、`components`、`layouts`、`composables`、`server`、`utils`、`plugins`、`middleware`、`lib`）中查找完整键名；动态拼接的键会误报，保持 warning。
-   **未翻译候选**：目标语言值与默认语言完全相同且默认值含中文；不阻断。
-   **重复文案**：只提示完全相同的值，是否上收由组件职责与加载边界决定。

### 7.2 package.json scripts（已落地）

```json
{
    "i18n:audit": "node scripts/i18n/audit-locale-keys.mjs",
    "i18n:audit:missing": "node scripts/i18n/audit-locale-keys.mjs --only=missing --fail-on-missing",
    "i18n:audit:duplicates": "node scripts/i18n/audit-duplicate-messages.mjs",
    "i18n:audit:hardcoded": "node scripts/i18n/audit-hardcoded-text.mjs",
    "i18n:audit:hardcoded:update": "node scripts/i18n/audit-hardcoded-text.mjs --update",
    "i18n:check-sync": "node scripts/i18n/check-locale-parity.mjs",
    "i18n:check-fallback": "node scripts/i18n/check-locale-fallback.mjs",
    "i18n:check": "pnpm i18n:audit:missing && pnpm i18n:check-sync && pnpm i18n:check-fallback && pnpm i18n:audit:hardcoded"
}
```

`i18n:check` 是 CI 的统一入口；`i18n:audit` 用于本地全量报告（未使用 / 未翻译为 warning）。

> `lint:i18n`（`@intlify/vue-i18n/*` 规则）与 `test:i18n`（`vitest.i18n.config.ts`）仍属于 M5 里程碑，待页面文案翻译准入后引入。

### 7.3 门禁接入（已落地）

-   **CI**：`test.yml`、`release.yml` 与 `regression-weekly.yml` 均执行 `pnpm i18n:check`；缺失键、结构不一致、Registry 违规与硬编码基线外新增都会阻断。
-   **Git Hook**：`lint-staged` 对 `i18n/locales/**/*.json` 执行缺失键与结构校验；对 `app.vue`、`pages`、`components`、`layouts`、`composables` 以及 `server` 的扫描范围（`api` / `utils` / `routes` / `middleware` / `templates`）执行硬编码中文审计。脚本忽略 lint-staged 传入的文件路径，始终审计全量范围。
-   **运行时测试**：`tests/unit/i18n/governance-scripts.spec.ts` 覆盖拍平、键差异、键名边界、硬编码扫描与 Registry 规则。

### 7.4 硬编码中文基线

`i18n/hardcoded-text-allowlist.json` 记录每个文件的中文行数基线：

-   新增文件或文件内中文行数增加 → blocker；
-   翻译后行数减少 → warning，运行 `pnpm i18n:audit:hardcoded:update` 收紧；
-   基线按文件计数而非行号，容忍同一文件内的等量替换；跨文件移动会被识别为「新增 + 可收紧」。

扫描范围：Vue 根模板（跳过 `<script>`、`<style>` 与 HTML 注释）、`composables/**/*.ts`、`server/api/**/*.ts`、`server/utils/**/*.ts`、`server/routes/**/*.ts`、`server/middleware/**/*.ts`、`server/templates/**/*.{ts,mjml}`；TypeScript 跳过块注释与整行注释。存量基线用于阶段 3 前的债务可视化，不扩大范围；`server/database`（Demo 种子）暂未纳入，随 M5 demo 模块处理。

## 9. 关键风险与应对

-   **翻译缺失**：通过审计脚本与 CI 报告阻止缺失键，预设 fallback 为中文。
-   **性能影响**：核心模块首屏加载，`admin-*` / `profile` / `security` / `oauth` / `sso` / `demo` / `email` 按路由或场景懒加载；不要把所有 JSON 塞进首屏。
-   **SEO 冲突**：`strategy: 'prefix_except_default'` + `alternate` 链接标记；`ui-ready` 语种不进 sitemap。
-   **better-auth 标识冲突**：认证层统一映射，业务层只使用项目内部 locale 标识。
-   **服务端一致性**：服务端翻译加载器与前端共享同一份 Locale Registry 与回退链。
-   **Zod 全局 locale 串语言**：禁用全局 `z.config(z.locales.*)`，只用 per-parse error map。
-   **邮件无用户偏好**：新增 `User.locale`；同步流程用请求 locale 兜底，异步通知用用户偏好。
