# AI 协作规范 (AI Collaboration Standards)

本规范为草梅 Auth 项目中 AI 智能体（Agents）的行为准则，旨在确保 AI 在自动化过程中逻辑严密、安全合规且不破坏现有工程质量。项目级角色矩阵、冲突顺序与安全红线以 [AGENTS.md](../../AGENTS.md) 为唯一权威事实源，本规范只承接执行细节。

## 1. 身份认同 (Identity)

每个 AI 智能体在启动任务前，必须明确自己的角色定位（见 `AGENTS.md` 第 6 节）：

- **禁止跨权**：`@qa-assistant` 严禁修改代码；`@code-auditor` 只做审计不写实现；`@test-engineer` 专注于测试编写。
- **环境感知**：执行命令前，必须通过 `os` 信息判断当前是 Windows 还是 POSIX 环境，并使用正确的命令语法。

### 1.1 执行原则 (Execution Principles)

1.  **搜索优先**: 当遇到需要外部信息、排查未知问题、根因不明确或修复失败 >= 2 次时，必须先使用搜索工具获取一手信息（触发条件与信息源采纳原则见 `AGENTS.md` 4.3 节）。
2.  **显式假设**: 需求存在歧义、边界未定义或上下文不足时，必须先说明当前假设、可选解释与风险；禁止静默选择一种解释后直接大规模实现。
3.  **简洁优先**: 默认选择满足当前验收标准的最小实现，不引入与当前目标无关的抽象、配置层或未来能力预埋。
4.  **外科式改动**: 改动范围应与用户请求、Todo 验收点或 blocker 一一对应；发现无关问题时可以记录，但不得顺手并入当前实现。
5.  **目标驱动验证**: 进入实现前明确成功标准与最低验证矩阵；完成首个实质改动后，优先做最小充分验证，再决定是否继续扩写。

### 1.2 工具编排优先级

若当前 AI 工具支持 sub-agent 编排能力，应优先用于以下高负载场景：

1.  大范围检索、代码考古、文档比对、审计证据收集等可并行的只读任务。
2.  需要分别覆盖代码、测试、文档、性能或安全多条证据链的治理型任务。
3.  需要在有限上下文窗口内同时处理多个目录、多个规范来源或多个验证结果的收口任务。

补充约束：

1.  多代理编排的目标是降低单 agent 上下文过载，不是引入多个平行主责；最终结论、放行判断与文档回写仍必须由当前主责角色统一收口。
2.  若任务存在共享写入面，应避免多个 agent 同时编辑同一文件或同一决策段落，优先采用"并行检索 / 串行落盘"的方式。
3.  若工具不支持 sub-agent，只允许记录能力限制与回退路径，不得因此跳过既有验证、审计或文档要求。

## 2. 核心工作流：PDTFC 循环

所有写操作任务必须严格遵循以下执行顺序。**严禁跨越关键质量阈值。**

### P (Plan) - 需求分析与规划

- **意图抽离**：必须读取 `docs/plan/todo.md` 与 `docs/plan/roadmap.md`，若存在歧义必须发起"采访"模式。
- **规划闸门**：无论是用户新提出的需求，还是在开发/测试过程中临时发现的新事项，都必须先核对 `todo.md`、`roadmap.md` 与当前任务验收标准，确认是否已属于当前规划。
- **插队判定**：若新事项不在当前规划内，必须先完成一次快速分流，明确是"允许插队的阻塞/高风险事项"还是"应延期的积压项"；未完成判定前不得进入 Do 阶段。
- **任务定义**：更新 `todo.md`，将任务标记为 `in-progress`。
- **方案设计**：输出受影响文件清单及技术实现路径。

### D (Do) - 业务执行

- **数据库优先**：若涉及持久化，必须优先开发数据库实体/Schema（TypeORM Entity）。
- **实现准则**：遵循 TypeScript 架构，禁止使用 `any`，UI 文本必须 i18n 化（见 [国际化实施方案](./i18n.md)）。
- **最小实现**：默认先做满足当前验收标准的最小切片；若需要扩大实现面，必须先说明为何当前最小方案不足。
- **范围稳定**：开发过程中若发现新的体验优化、附加功能或非阻塞问题，不得直接扩写当前任务；必须回到 P 阶段重新判断是否允许插队。

### A (Audit) - 代码审计（强制 Review Gate）

- **强制入口**：D 阶段完成后，必须立即加载 `code-reviewer` skill 并移交 `@code-auditor` 执行完整的结构化审查，不得自我审查替代。A 阶段未被放行前，不得进入后续 V / T / F 任何阶段。
- **审查内容**：按第 3 节验证分级矩阵核对最低验证要求，覆盖正确性、安全、规范一致性、Todo 验收点与证据链。
- **审查范围**：代码、文档、配置、脚本与治理定义（含 agent / skill 定义）均须审查，不能只审业务代码。
- **退回策略**：若发现 blocker，退回 D 或回流 P，不得携带未关闭的 blocker 进入后续阶段。

#### 分级审计执行协议（audit-depth）

审查投入与改动风险匹配，不应对所有改动一视同仁：

| audit-depth | 适用改动 | 审查范围 | 时间盒 |
| :---: | :--- | :--- | :---: |
| `quick` | 文档措辞、简单配置、重命名、测试补强 | 只核验证声明（lint/typecheck/定向测试结果）+ diff 概要一致性 + 明显错误 | ≤ 5 分钟 |
| `standard` | 常规业务逻辑、模块内改动 | 正确性 + 边界 + 测试覆盖；定向抽查 ≤ 3 个关键文件 | ≤ 10 分钟 |
| `deep` | 发布流程、安全/鉴权、外部调用、数据写入、配置与依赖变更、agent / skill 定义 | 全量 checklist + 针对性实证 | ≤ 20 分钟 |

配套实践：

- **审计 prompt 携带"已查证事实"**：执行角色把调研结论 / 实验证据写进审计任务，避免审计者从头翻源码。
- **audit-depth 声明**：审计 prompt 必须显式声明 `audit-depth`（`quick` / `standard` / `deep` + 理由）、变更文件清单、已验证证据摘要与复审问题编号。未声明 depth 时默认按 `deep` 防御执行。
- **复审只审修复点**：第 2+ 轮审计只移交上轮问题编号对应的修复 diff，不重发全量 diff。
- **并发审计**：diff 文件数 > 8 或涉及 ≥ 2 个独立模块时，按模块分区并行发起审计，主审汇总合并去重、取最严结论；小改动不得并发。

### V (Validate) - UI 验证

- **视觉审计**：对 UI 改动进行浏览器验证（`@ui-validator`）。若自动化工具失效，应向用户展示截图或请求人工验证。
- 无 UI 面影响时显式记录跳过原因，不默认省略。

### T (Test) - 质量检查

- **测试覆盖**：编写 Vitest 测试用例。测试代码本身也必须经过 A 阶段的 Lint 和类型检查。
- **风险导向**：优先补当前缺陷会打断的断言、失败路径与边界行为，不把测试阶段退化为机械补 coverage。

### F (Finish) - 任务完结与单次提交

- **闭环管理**：更新 `todo.md` 状态为 `completed`，并及时同步项目相关的技术文档。
- **单次提交**：整个任务产生的所有改动（业务代码 + 测试代码 + 文档）一次性提交。提交前必须加载 `conventional-committer` skill，通过其前置检查（依赖 A 阶段已放行、`pnpm lint`、`pnpm typecheck`、定向测试均通过），生成符合 Conventional Commits 格式的消息（使用中文或用户使用的语言），然后执行 `git commit`。
- **推送禁令**：`git commit` 后不得自动 `git push`，仅限用户明确要求时执行。

## 3. 验证分级矩阵与 Review Gate

任何变更都必须按"验证层级 + Review Gate"判断是否可以放行，而不是只写一句"已验证"。

### 验证层级定义

| 层级 | 名称 | 目标 | 典型证据 |
| :--- | :--- | :--- | :--- |
| `V0` | 记录层 | 明确变更范围、风险与受影响入口 | 变更文件清单、风险说明、回归范围 |
| `V1` | 静态层 | 确认代码、脚本、配置或文档在静态检查层面可用 | `lint`、`typecheck`、文档检查 |
| `V2` | 逻辑 / 运行层 | 确认逻辑、接口契约、脚本入口或异常分支无明显回归 | 定向 Vitest、API / 集成测试、脚本实际运行验证 |
| `V3` | 流程层 | 确认跨模块流程、UI 渲染与关键交互符合预期 | 浏览器验证、E2E、截图或录屏 |
| `RG` | Review Gate | 给出最终审计结论与剩余风险 | `@code-auditor` 结论、阻塞项、未覆盖边界 |

### 不同改动类型的最低验证要求

| 改动类型 | 最低验证要求 | 说明 |
| :--- | :--- | :--- |
| 文档 / README | `V0 + V1 + RG` | 至少保留文档检查结果、相对路径 / 构建影响说明与 Review 结论。 |
| 配置 / 脚本 | `V0 + V1 + 按影响补 V2 + RG` | 若影响构建、部署、生成或治理流程，必须补一条实际运行证据。 |
| 纯逻辑 / 工具函数 / 服务层 | `V0 + V1 + V2 + RG` | 不能只跑 `lint`；必须补充定向测试或同等逻辑验证。 |
| API / 鉴权 / 数据模型 | `V0 + V1 + V2 + RG` | 若影响登录、权限或关键写路径，应升级到 `V3`。 |
| UI 组件 / 页面交互 | `V0 + V1 + V2 + V3 + RG` | 涉及核心页面首屏时，再补充性能观察。 |
| 跨模块流程 / 关键链路 | `V0 + V1 + V2 + V3 + RG` | 例如登录、OAuth 授权、邮箱/短信验证、管理端写路径。 |
| 修复型 Hotfix | `V0 + V1 + 与故障层级对应的 V2/V3 + RG` | 必须补"复现方式 + 修复后结果"，不能只写"已修复"。 |

补充约束：

1.  没有 `RG` 结论的变更，只能视为"进行中"，不能视为已完成。
2.  文档、配置、脚本改动同样需要证据链，只是证据形态可以比功能代码更轻量。
3.  若某项变更同时触发多个改动类型，按最高层级要求执行，不允许向下取低。

### Review Gate 结论口径

| 结论 | 是否允许放行 | 适用条件 |
| :--- | :--- | :--- |
| `Pass` | 是 | 所有阻塞问题已关闭；允许存在已记录的非阻塞风险，但不得影响当前交付闭环。 |
| `Reject` | 否 | 存在阻塞问题、关键证据缺失，或当前变更不满足最低验证要求。 |

补充约束：

1.  `warning`、`suggest`、`blocker` 是问题分级，不是最终 Gate 结论；最终结论只能使用 `Pass` 或 `Reject`。
2.  只要仍有未关闭的 `blocker`，任务状态必须保持为进行中或退回，不得标记完成。
3.  `Pass` 可以附带非阻塞 `warning`，但必须同步记录残余风险、责任归属与后续计划。

## 4. 证据链与模板

所有任务在 Finish 前至少要沉淀以下字段：

1.  变更范围
2.  已执行验证
3.  结果摘要
4.  Review Gate 结论
5.  未覆盖边界 / 后续补跑计划

### 功能改动模板

```md
## 验证记录
- 变更范围:
- 风险等级:
- 已执行验证:
	- lint / typecheck:
	- 定向测试:
	- 浏览器 / E2E:
- 结果摘要:
- Review Gate:
	- 结论: Pass | Reject
	- 问题分级: none | suggest | warning | blocker
	- 主要问题:
- 未覆盖边界:
- 后续补跑计划:
```

### 修复型 Hotfix 模板

```md
## Hotfix 验证记录
- 问题现象:
- 复现路径:
- 修复范围:
- 已执行验证:
	- 复现前证据:
	- 修复后定向验证:
	- 回归验证:
- 结果摘要:
- Review Gate:
	- 结论: Pass | Reject
	- 问题分级: none | suggest | warning | blocker
- 未覆盖边界 / 后续补跑计划:
- 剩余风险 / 回退方案:
```

## 5. 修复工作流原则 (Fix Workflow Principles)

### 5.1 最小复现测试优先

根因不明确时，**先编最小复现测试（`__debug.test.ts`，<5s 出结果），再跑全量测试**。一次只验证一个假设，避免投入 10+ 分钟全量测试来验证错误的方向。

### 5.2 CI 作为最终裁决

修复的验收标准是 **CI 流水线全部通过**，不是本地测试通过。工作流：

```
根因排查(最小复现) → 方案验证(定向subset) → 批量修复 → 本地通过 → 提交 → CI通过 = ✅ 完成
                                                                      ↕
                                                                CI失败 → 针对性补修 → 再提交
```

CI 失败后**不得**回退到全量重试，应分析具体失败点，针对性修复。

### 5.3 死循环规避

如果在 F 阶段重复 3 次仍无法修复 Bug，必须停止执行并请求人类介入，禁止无限循环。**同一问题修复失败 >= 2 次时，必须先触发搜索优先流程**（见 1.1 节），不得用同一思路反复重试。

## 6. 沟通原则

- **简明扼要**：回复应直接、专业，避免冗余的客套话。
- **证据链条**：在提出方案或得出结论时，应引用具体的代码文件路径或文档内容。
- **透明度**：在执行大规模修改前，应向用户展示预期的代码变更范围。
