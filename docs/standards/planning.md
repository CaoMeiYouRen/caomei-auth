# 规划规范 (Planning Standards)

本文档定义草梅 Auth 的规划载体、新需求准入、条目粒度、进度可视化与归档规则。项目级角色矩阵、冲突顺序与安全红线以 [AGENTS.md](../../AGENTS.md) 为唯一权威事实源；本文只负责“需求如何进入规划、如何实施、如何归档”。

## 1. 规划载体

| 载体 | 文件 | 职责 |
| :--- | :--- | :--- |
| 路线图 | [roadmap.md](../plan/roadmap.md) | 中长期方向与已授权阶段的里程碑；方向不等于启动授权，候选详情留在 backlog |
| 待办事项 | [todo.md](../plan/todo.md) | 当前已授权阶段的进度表、大条目与小条目；不保留未完成项汇总，未完成候选只在 backlog 维护 |
| Backlog | [backlog.md](../plan/backlog.md) | 已评估候选池、候选阶段组合、未完成项汇总与已决策但尚未登记阶段的过渡态 |
| 阶段归档索引 | [todo-archive.md](../plan/todo-archive.md) | 已收口阶段的索引表与分片指针；只保留索引，不保留阶段正文 |
| 归档分片 | `docs/plan/archive/` | 阶段正文分片：`todo-archive-phases-*.md` 与 `roadmap-phases-*.md` |
| 已完成归档 | [completed-work.md](../archive/completed-work.md) | 历史 / 能力混合视图（主题 + 阶段，§1–§7 主题式、§8–§15 阶段式）；自 2026-11-20 起冻结，不再承载新阶段交付摘要 |

> `completed-work.md` 冻结后只允许补指向 [todo-archive.md](../plan/todo-archive.md) 的导航行、一次性冻结说明与勘误，正文保持原样。
> 不再新增与上述职责重叠的规划文件。已完成 / 已收口的专项子规划（如 [zod-migration.md](../archive/zod-migration.md)）与历史重构总结（[refactor.md](../archive/refactor.md)）统一迁入 `docs/archive/`，由归档或 backlog 引用（阶段正文除外，见上表归档分片行）；新重构候选统一登记 backlog。

## 2. 流转

```text
新需求 → 评估 → backlog.md → 用户明确决策 → todo.md 当前阶段 → 小条目实施 + 提交 + 审计
                                                      ↓
                                       阶段收口 → todo-archive.md 索引 + archive/ 分片
                                                      ↓
                                                 roadmap.md 阶段摘要
```

## 3. 准入规则

1. **Backlog 优先**：功能、重构、体验优化、集成、监控等新需求先评估并登记到 `backlog.md`，不得直接写入 `todo.md`。
2. **不自动升级**：未经用户明确授权，backlog 候选不得进入 `todo.md`；AI 不得推断某条应作为最高优先级并默认启动。
3. **不擅自规划下一阶段**：`roadmap.md` 中未授权方向与 backlog 候选不构成启动授权；下一阶段范围须经需求评估与用户决策后登记。
4. **插队例外**：以 [AGENTS.md §5.1.2](../../AGENTS.md#51-迭代中途发现事项处理规则) 为准，仅以下情形可直接进入当前阶段，并须在任务记录或提交说明中写明“为何插队”：
    - 阻塞当前交付；
    - 明确功能回归；
    - 高风险安全 / 合规问题；
    - 导致当前任务无法闭环的基础缺陷。
5. **范围降级同样须用户裁定**：已授权条目内的子能力不自动升降级；先取证（用量 / 影响面 / 快照日期），再交用户决策，决策后同步全部载体。
6. **决策落定须同步全部载体**：用户决策后，除登记者外须同步受影响的规范、设计文档、AI 资产（skills / agents）与 `.session/`；只改一处会让仓库并存两套口径。
7. **完成态不得预写**：`todo.md` 的完成态与 Review Gate 的绑定以 [AI 协作规范](./ai-collaboration.md) F 阶段为准；规划载体不得提前写入未落地的完成状态。

## 4. 粒度模型

| 层 | 定义 | 必填字段 | 提交 | 审计 |
| :--- | :--- | :--- | :--- | :--- |
| 阶段 | 一次授权范围 | 目标 / 容量基线 / 执行顺序 / 不做什么 | — | — |
| 大条目 | 一个可独立验收的交付包 | 8 要素：目标 / 优先级 / 范围 / 验收标准 / 不做什么 / 依赖 / 交付物 / 风险与缓解 | 1–N 次 | 至少 1 轮 |
| 小条目 | 可独立提交的最小单元 | 目标 / 验收标准 / 交付物 / 依赖（其余继承大条目） | 默认 1 次 | 跟随本条目提交 |

- **数量约束**：大条目下限 3（沿用原「3–6 条主线」的下限）、默认 4–6、**上限 8**；使用第 7–8 个时须在阶段头写明「为何不拆阶段」，8 是上限而非目标值。每个大条目 1–5 个小条目；单阶段小条目建议 10–15，低于 10 条须写明「为何不再合并」，超过 15 须写明「为何不拆阶段」，达到 20 条及以上视为阶段容量告警，须在登记时取得用户确认（阶段 3 的 20 条为历史先例，不构成常态）。
- **术语映射**：原「主线」并入「大条目」，「原子条目」等同「小条目」，现行规范统一用后者；阶段 1–9 的历史记录与 skill / agent 定义中的旧称不改写，`AGENTS.md` / [Git 规范](./git.md) 中的「原子条目」按本映射理解（`AGENTS.md` 改名需用户授权，未授权前保留原词）。
- **字段分层是硬要求**：小条目只写 4 项，不复制大条目的 8 要素，避免 `todo.md` 与归档分片体量翻倍。
- **提交与审计粒度**：一个**条目提交**只承载一个小条目，不得跨条目；同一个小条目可以包含多次条目提交（实现 / 测试 / 视觉基线重采 / 复审修复），所有提交说明指向同一条目 ID。默认目标是每个小条目 1 次提交，分次提交时在条目内简述分次原因（历史阶段普遍存在实现 / 测试 / 视觉基线的分次提交）。不承载小条目的提交有两类，按 [AGENTS.md](../../AGENTS.md) §7.3.4 的规划 / 治理类口径处理（该条未覆盖的回填 / 收口例外已在 backlog 登记待同步）：① **回填提交**——只补齐进度表字段，不归属任何小条目、不计入容量；② **阶段收口提交**——归档切片、索引追加、roadmap 指针与完成项清理，天然跨多个大条目。该口径与 AGENTS.md §7.3 及 [Git 规范](./git.md) §3 的「一个提交仅关联一个条目」同向。
- **小条目规模**：单个小条目建议不超过 **10 个文件 / 800 行新增**；生成物（如 `pnpm-lock.yaml`、构建产物）不计入，但须与触发变更同提交。超阈值时必须拆分为多个小条目；未拆分且无正当理由的改动，`@code-auditor` 有权 Reject。
- **ID**：大条目按阶段内顺序编号（`M1`、`M2` 等），小条目为 `<大条目ID>.<序号>`（`M1.1`、`M1.2`）；不要求跨项目一致，但**必须**项目内唯一，且能在进度表「提交」列定位到实际提交。存量 ID（含 `M5-2` 式）不改；重编号或拆分后须回扫 `todo.md`、`roadmap.md`、backlog 与 `.session/` 中的全部引用。
- **阶段编号**只在授权启动时分配：编号取“已有最大编号 + 1”，仅授予经用户明确授权启动的阶段；未授权工作不预留编号。
- **前向统一**：自下一阶段（阶段 10）起按本节与 §7 / §8 执行；阶段 1–9 保留原样（不回填、不重编号）。阶段 3–9 的登记与收口记录、阶段 2 的登记记录见 `docs/design/governance/`，阶段 2 的交付摘要见 [completed-work.md](../archive/completed-work.md) §8，阶段 1 见该文件 §1–§7（主题式近似映射）；摘要均不因本次升级而改写。

## 5. 状态同步

- **开发前**：对齐 `roadmap.md` 与 `todo.md`，确认条目已获授权。
- **开发后**：同步 `todo.md` 的进度表（状态 / 审计结论 / 提交回填）与条目内的验收结论；阶段收口时按 §8 把阶段正文迁入归档分片并登记索引，`completed-work.md` 不再追加。
- **归档清理**：已完成 / 已归档条目不得在 `todo.md`、`backlog.md` 保留交付摘要、归档指针或“闭环整理”段；`todo.md` 只保留“当前阶段状态（可为无进行中阶段）+ 进度表 + 当前阶段大 / 小条目”，`backlog.md` 只保留尚未进入阶段的候选与未完成项汇总（仅指未启动候选的聚合，不含进行中阶段小条目）。`todo.md` 不保留未完成项汇总或跨阶段清单，避免两份口径。阶段收口时，未完成小条目迁入 `backlog.md` 候选区，并移除阶段编号与验收状态。
- **`.session/` 同步**：发生阶段登记、阶段归档或阶段范围变更时，须在同批同步 `.session/current-task.yaml` 与 `.session/runtime-state.json` 的阶段态。`.session/` 为 git-ignored 任务态，不进提交物，但会决定下一次 session 的恢复起点。
- **Session 收尾**：按 `full-stack-master` 的 Session 协议更新任务态；`.session/wisdom.md` 活跃条目达到阈值时提醒蒸馏。

## 6. 审计

本规范由 `@code-auditor` 在 Review Gate 中检查，至少覆盖：

1. 新事项是否有明确落点（当前阶段 / backlog），是否越阶段容量私自扩容；
2. `todo.md` 是否只含已授权阶段条目，完成态是否与 RG 结论同批；
3. 归档后 `todo.md` / `backlog.md` 是否已清理完成项；
4. 决策落定后受影响载体与 `.session/` 是否已同步；
5. 进度表行数是否等于正文大条目数、状态值是否在 §7 的四个取值内；
6. 归档索引是否覆盖全部 `todo-archive-phases-*` 分片（倒序、无重复、无正文），分片命名是否匹配 §8；
7. 条目提交是否只承载一个小条目，回填 / 收口提交是否被误计容量（口径见 §4 与 §7）；
8. `completed-work.md` 是否被改写（除导航行、一次性冻结说明与勘误）。

违规按 blocker / warning 分级。未经授权把候选升级为当前阶段、预写未落地的完成态、改写 `completed-work.md` 正文、进度表与正文不一致，按 blocker 处理。

## 7. 进度表

`todo.md` 当前阶段标题下第一张表为阶段进度表，必需 6 列（均为必需）；项目可增补列，不得删减必需列。格式示例（示意值，非真实提交）：

| 大条目 | 小条目 | 状态 | 提交 | 审计 | 容量（计划→实际） |
| :--- | :--- | :--- | :--- | :--- | :--- |
| M1 归档索引与分片 | 3/3 | 已闭环 | `a1b2c3d`、`b2c3d4e`、`c3d4e5f` | R1 Pass | 3 → 3 commits |

- **行 = 大条目**，行数必须等于正文大条目数；`小条目` 列写「已闭环 / 总数」。
- **状态**收敛为四值：`未开始` / `进行中` / `已闭环` / `已阻塞`，不使用其它写法。
- `提交` 列写该大条目全部条目提交的短 SHA（按时间顺序、「、」分隔）；超过 3 个时写最近一个并注明总数（如 `c3d4e5f 等 5 个`），全量清单由 §8 归档块的「提交清单」承载。SHA 只能在提交产生后回填：允许滞后到下一个小条目的收尾提交，阶段收口提交之前必须填齐；回填提交只改表格字段，不归属小条目、不计入容量。
- `审计` 列写 Review Gate 结论与轮次（如 `R1 Reject → R2 Pass`）。
- `容量` 列默认单位为 commits，可按阶段改用 files 或行数，同一阶段内保持一致；实际值在阶段收口时填齐。
- 状态与审计结论随条目收尾提交更新；不得预写未落地的完成态，也不得预写尚未产生的 SHA。

## 8. 归档载体

| 项 | 约定 |
| :--- | :--- |
| 索引 | `docs/plan/todo-archive.md`，只保留 4 列索引表与分片规则，不保留阶段正文 |
| 分片目录 | `docs/plan/archive/` |
| 分片命名 | `todo-archive-phases-<起>[-<止>].md`、`roadmap-phases-<起>[-<止>].md`；区间连续，todo 与 roadmap 分片分开，不得合并为同一文件（两族命名不对称沿用上游跨项目约定，优先保证跨仓库一致） |
| 索引表 | 固定 4 列：阶段 / 主题 / 归档文件 / 归档日期；覆盖全部 `todo-archive-phases-*` 分片，按归档日期倒序、同一路径不重复、不含阶段正文；`roadmap-phases-*` 分片不登记本索引，由 `roadmap.md` 的里程碑指针维护 |
| 归档块必填 | 阶段名与时间 / 大条目清单与状态 / 提交清单（只列条目提交，回填与收口提交单列或省略）/ 质量门结果 / Review Gate 结论与轮次 / 未覆盖边界 |

- **阶段收口流程**：把阶段正文（含进度表与全部大 / 小条目）按 `^##` 边界切片迁入 `todo-archive-phases-*` 分片 → 在 `todo-archive.md` 索引追加一行（保持倒序）→ 在分片头写归档块 6 项 → 已收口里程碑详情迁入 `roadmap-phases-*` 分片并在 `roadmap.md` 更新指针 → 清理 `todo.md` 与 `backlog.md` 中的完成项 → 同步 `roadmap.md` 里程碑状态。
- **`completed-work.md` 冻结**：阶段收口不再向其中追加交付摘要；仅允许补导航行、一次性冻结说明与勘误，正文保持原样。
- **不回填历史**：阶段 1–9 不补建索引与分片，避免重写历史；自阶段 10 起逐阶段登记。
- **改名保真**：因命名规则调整而改名时，`git diff` 只允许出现文件重命名与因路径变化产生的链接 / 锚点修正，不得顺带改正文、调顺序或补字段。
- **主文件行数**：`todo-archive.md` 建议不超过 400 行；超出时只压缩索引说明，不把阶段正文迁回主文件。
